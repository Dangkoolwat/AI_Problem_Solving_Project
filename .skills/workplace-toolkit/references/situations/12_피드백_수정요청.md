# 피드백과 수정 요청

> 이 파일은 `.skills/workplace-toolkit/SKILL.md`의 상황별 안내입니다. 공통 원칙은 SKILL.md를 먼저 읽습니다.

**언제:** 동료·팀원의 작업물을 리뷰하거나, 수정을 요청하거나, 협업 중 불편한 점을 전달하거나, 구체적으로 칭찬·인정하고 싶을 때. 단순한 메일 답장은 `06_답장_초안.md`, 무리한 부탁 거절·일정 조율은 `13_거절_일정조율.md`를 쓴다.

## 기본 흐름 (상황 → 관찰된 행동 → 미친 영향)

사용자에게는 방법 이름보다 "**피드백과 수정 요청**"처럼 얻는 결과로 안내한다. SBI(Situation–Behavior–Impact) 이름은 사용자가 원할 때만 쓴다.

평가나 추측 대신 아래 세 단계를 바탕으로 초안을 정리하고, 필요하면 다음 제안이나 확인 질문을 한 문장 덧붙인다.

1. **상황 (Situation):** 언제, 어떤 회의·문서·작업에서 일어난 일인지 구체적인 시점과 맥락을 적는다.
2. **관찰된 행동 (Behavior):** "성의가 없다", "부주의하다" 같은 판단 대신, 실제로 보거나 들은 사실·행동만 적는다.
3. **미친 영향 (Impact):** 그 행동 때문에 일정·결과물·협업 흐름이나 내 업무에 어떤 영향이 생겼는지 담백하게 적는다.
4. **다음 제안 또는 확인 질문 (선택):** 수정을 원하면 원하는 변화나 확인하고 싶은 점 한 가지를 덧붙인다.

## 내놓을 선택지

아래는 출발점이다. 상황에 맞게 2~3개로 추려 얻는 결과·필요한 것·아쉬운 점을 한 줄씩 보여 주고, 맞아 보이는 하나를 의견과 이유로 먼저 밝힌다. 사용자가 이미 방향을 정했으면 다시 고르게 하지 않는다.

| 선택지 | 얻는 결과 | 필요한 것 | 아쉬운 점 |
| --- | --- | --- | --- |
| 부드러운 수정 요청 | 좋은 점 한 줄 + 사실·영향 기반 수정 요청 초안 | 수정할 부분과 이유 | 핵심 요청이 흐려지지 않게 다듬어야 함 |
| 협업 불편 사실 전달 | 감정 대신 상황·행동·영향만 담은 대화·메신저 초안 | 실제 일어난 일과 영향 | 말투가 딱딱하게 느껴질 수 있음 |
| 구체적 칭찬·인정 | 어떤 행동이 어떻게 도움이 됐는지 짚는 메시지 | 고마웠던 실제 행동 | 길어지면 형식적으로 보일 수 있음 |

**의견을 정하는 기준:** 작업물 리뷰·수정 요청은 첫째, 반복되는 협업 문제는 둘째, 팀원 격려·감사는 셋째를 권한다.

## 지켜야 할 원칙

- 사용자가 말하지 않은 상대의 의도·감정·성격("일부러 미룬 것 같다", "관심이 없다")을 추측하거나 단정하지 않는다.
- 구체적인 상황·행동·영향이 메모에 빠져 있으면 지어내지 않고 `[확인 필요]`로 남기거나 한 번에 1~2가지만 묻는다.
- 괴롭힘·차별·징계·법적 분쟁처럼 안전이나 권리가 걸린 사안은 피드백 초안으로 해결하려 하지 말고, 회사의 담당 창구나 전문가 상담을 먼저 안내한다.
- 초안까지만 작성하며, 실제 메신저·메일 발송이나 전달은 사용자가 직접 확인하고 결정한다.

**결과 모습:** 상황에 맞춘 피드백·수정 요청 초안과 보내기 전에 사용자가 확인할 점. 문장이 어색하면 `.skills/humanize-korean/SKILL.md`로 이어서 다듬는다.
