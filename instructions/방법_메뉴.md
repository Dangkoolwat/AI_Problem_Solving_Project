# 방법 메뉴

어떤 방법을 제안할지 고르거나 여러 스킬을 엮어 워크플로우를 짤 때 읽는다. 고민에 가까운 줄을 찾아 후보를 2~3개로 추리고, `AGENTS.md` 4절의 형식(얻는 결과·필요한 자료와 수고·아쉬운 점·의견)으로 제안한다. 고른 방법을 실제로 적용할 때 "읽을 곳"의 파일을 연다. 이 표만 보고 방법의 세부 절차를 지어내지 않는다.

방법에는 정해진 순서가 없고 정답도 없다. 사용자가 평소 쓰는 방식이 있으면 그것이 먼저다. 방법 하나만 체험하고 싶다는 요청에는 그 방법만 적용한다. 방법 이름을 사용자에게 외우게 하지 않는다. 이름보다 얻는 결과를 먼저 말한다. 표에 없는 방법도 상황에 맞으면 제안할 수 있다.

## 1. 고민별 방법

스킬 경로는 `.skills/` 기준이다. `job/…`은 `job-search-toolkit/references/situations/`, `work/…`은 `workplace-toolkit/references/situations/`의 파일이다.

### 비슷한 방법이 겹칠 때

같은 고민에 방법이 둘 이상 걸리면 아래 기준으로 하나를 먼저 고른다. 입구가 달라도 같은 방법으로 풀리게 하기 위한 기준이다.

| 겹치는 것 | 먼저 쓸 것 | 다른 쪽을 쓰는 때 |
| --- | --- | --- |
| 뭐부터 할지: `thinking-toolkit`의 지금 할 일 하나 고르기 / `job/09_우선순위_대조.md` | 지금 할 일 하나 고르기 | 할 일이 모두 지원 준비이고 공고 마감·경험 대조가 필요할 때 `job/09` |
| 선택 비교: `thinking-toolkit`의 가정과 선택 비교 / `work/10_대안비교_재사용.md` | 가정과 선택 비교 | 업무 대안을 비교한 뒤 반복 업무로 재사용할 때 `work/10` |

| 핵심 전달: `clear-summary` / `workplace-toolkit`의 보고 구성 | 이미 만든 결과를 줄여 전할 때 `clear-summary` | 보고를 처음부터 쓸 때 `workplace-toolkit` |

| 메일: `work/06_답장_초안.md` / `persuasion-writing` | 받은 메일에 답하거나 상황을 알릴 때 `work/06` | 먼저 보내서 협조·참여·승인을 받아야 할 때 `persuasion-writing` |

## 2. 전용 스킬이 없는 고민

아래 고민은 전용 스킬이 없다. 기존 방법을 빌려 조합하고, 전용 방법이 없다는 점을 숨기지 않는다.

| 고민 | 빌려 쓸 방법 | 지켜 줄 것 |
| --- | --- | --- |
| 이직할지 남을지 | 가정과 선택 비교 → 여러 관점으로 점검하기 → 미리 어려움 살펴보기 | 이미 결정했으면 흔들지 않고 "해 보면서 확인할 점"으로 바꾼다. 계약·법 판단은 하지 않는다 |
| 탈락 후 돌아보기 | 먼저 살펴보기, 공고와 서류 대조(`job/09`), 돌아보기와 조정 | 탈락 이유를 확정하지 않는다. 탓하지 않는다 |
| 처우 협상 준비 | 우선순위 정리(가정과 선택 비교), 다른 관점에서 보기, 답장 초안(`work/06`) | 출처 없는 시세 숫자를 만들지 않는다. 계약 조항의 법적 의미를 확정하지 않는다 |
| 어려운 대화 준비 | 바라는 것 한 문장 정하기, 다른 관점에서 보기, 첫 문장 연습 | 상대의 마음을 단정하지 않는다. 괴롭힘·차별·법 문제는 담당 창구와 전문가를 먼저 안내한다 |
| 발표 준비 | 핵심부터 전달(`clear-summary`), 기획의 구조 잡기(`planning-toolkit`), 미리 어려움 살펴보기 (짧은 발언은 `job/10_면접연습.md`의 1분 답변 짜기) | 자료에 없는 숫자를 넣지 않는다. 파일 제작 가능 여부를 확인한다 |
| 업무 인수인계 | 업무별 현황(`work/08`), 반복 업무 순서 적기, 다른 관점에서 보기(받는 사람) | 비밀번호·접속 정보를 문서에 적지 않는다 |
| 돈 관리 | 가정과 선택 비교, 표 자료 분석(`data-toolkit`) | 합계와 단위를 사용자가 직접 확인하게 한다. 투자·대출 판단은 하지 않는다 |
| 인간관계 고민 | 먼저 듣기 → 먼저 살펴보기(사실과 해석 나누기) → 다른 관점에서 보기 | 결과물을 강요하지 않는다. 조언은 사용자가 원할 때 한다. 오래 힘들어 보이면 믿을 만한 사람이나 전문가의 도움을 권한다 |

## 3. 엮어 쓰는 예

워크플로우를 제안할 때의 출발점이며 따라야 할 순서가 아니다. 사용자가 여러 방법을 이어 쓰고 싶어 할 때만 제안한다. 순서와 단계는 사용자의 상황에 맞게 바꾸고, 계획을 보여 준 뒤 승인받아 실행한다.

| 목표 | 엮는 순서 |
| --- | --- |
| 공고에 맞춘 지원 서류 | 공고 비교 → 경험 발굴(4R) → 공고와 경험 연결 → 스타 초안 → 한글 다듬기 → 면접 연습 |
| 흩어진 자료로 결정 요청 보고 | 업무 소통 기록 → 근거 대조 → 왜·무엇을·어떻게·어떤 조건 → 핵심부터 전달 |
| 매주 하는 보고 줄이기 | 주간 보고 한 번 작성 → 워크플로우 저장 → 다음 주 새 자료로 결과 갱신 |
| 취업 준비 시작 | 그로우 → 직무 탐색 → 스마트 목표 → 실행 의도 → 돌아보기와 조정 |
| 관심 주제를 한 장으로 | 자료 조사 → 핵심부터 전달 → 인포그래픽 |
| 기획안에서 발표까지 | 문제 정리 → 기획 초안 → 관점 점검 → 발표 개요 |
| 모집글·안내문·설득 제안서 | 다른 관점에서 보기 → 행동을 이끄는 글 → 한글 다듬기 |
| 큰 문제 풀기 | 큰 문제 정리하기 → 생각 넓히기 → 가정과 선택 비교 → 일을 작게 나누기 (사용자가 원하는 곳에서 멈춘다) |
| 전공 원서 한 단원 공부 | 글 마련 → 큰 그림부터 풀어 읽기 → 내 말로 설명해 보기 → 문제로 꺼내 보기 → 간격을 두고 다시 보기 |
| 시험 준비 | 시험 범위로 점검하기 → 약한 단원을 문제로 꺼내 보기 → 틀린 문제 돌아보기 → 간격을 두고 다시 보기 → 모의고사 풀기 → 점수를 잃은 곳만 짧게 다시 보기 |

수강생용 사례는 `docs/cases/`에 있다. 사용자가 사례를 언급하거나 요청하면 해당 파일을 읽는다.
